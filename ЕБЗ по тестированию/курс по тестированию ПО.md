### исследовательское тестирование

> изучение продукта во время работы с ним

применяется: 
- при быстром знакомстве с новым сервисом
- если нужно в сжатые сроки дать ОС по функционалу или продукту в целом
- в конце тестирования, чтобы удостовериться, что ничего не пропустил

чтобы проверить функционал, требования которого неизвестны, можно использовать чит-листы.

> **чит-лист** - список типовых проверок для тестирования данных заранее известного формата

#### подходы к исследовательскому тестированию:
##### сессионное тестирование

1. определить конкретную цель (*например, новую функцию*)
2. выделить ограниченный промежуток времени
3. проверить целевую функциональность в течение выделенного времени
##### метод тест-туров

1. определить направление тестирования (*например, все формы оплаты в системе*)
2. выделить ограниченный промежуток времени
3. проверить выбранное направление в течение выделенного времени


### эвристики тестирования

> совокупность комплексов и методов, помогающая при тестировании

#### *SFDPOT* - эффективный инструмент для генерации тестовых идей

	s - структура - проверяем, из чего состоит приложение
	f - функциональность - проверяем, что приложение делает и как с ним взаимодействовать
	d - данные - как приложение работает с данными
	p - платформа - кроссплатформенность, кроссбраузерность, взаимодействие со сторонними программами (антивирусы, расширения и т.д.)
	o - использование - какая ЦА, как и почему используют продукт, с помощью чего заходят, почему и где происходит неправильное использование
	t - время - быстродействие работы приложения в различных условиях

#### *FEW HICCUPPS* - чтобы учесть внешние факторы

	f - знакомые проблемы - чтобы учитывать уже знакомые ошибки при тестировании похожих компонентов
	e - понятность - поведение системы должно быть легко объяснимо
	w - реалистичность - система должна соответствовать реальному миру
	
	h - история - вспомнить, как продукт работал раньше
	i - имидж - внешний вид сервиса должен соответствовать образу заказчика
	c - похожие продукты
	c - требования - соответствие заявленным характеристикам
	u - ожидания пользователей - собирать ОС от пользователей
	p - продукт - сохранение единых правил внутри продукта
	p - назначение - продукт должен решать проблему, для которой был создан
	s - законы и стандарты



### тестирование на основе рисков

#### подход к тестированию на основе рисков:

1. определить риски и подверженность им отдельных функциональных частей
2. создать список функциональных частей, распределенных по рискам
3. написать тесты по списку функциональности
4. начать тестировать с части, которая больше всего подвержена рискам
#### источники рисков:

1. сам продукт
2. команда разработки
3. пользователи



### техники тестирования
#### классы эквивалентности

>набор входных или выходных данных, которые обрабатываются программой одинаково, приводя к одному результату

по большей части применяются для проверки элементов программ.
##### этапы работы:

1. взять все тесты, которые нужно провести
2. разделить на группы по схожим параметрам и одинаковому результату
3. провести хотя бы по одному тесту для каждого класса

>**позитивное тестирование** - подход, при котором проверяется работа программы при использовании допустимых данных и сценариев

>**негативное тестирование**  - подход, при котором проверяется устойчивость системы к некорректным данным, нештатным ситуациям или недопустимым действиям пользователя

#### граничные значения

>техника тест-дизайна, проверяющая поведение системы на краях допустимых диапазонов входных данных
##### этапы работы:

1. выделить классы эквивалентности
2. определить границы классов
3. определить граничные значения для проверки
##### типы границ: 

- произвольные - определяются логикой продукта
- логические/физические
- технологические

#### диаграммы состояний и переходов

>графическая модель (диаграмма UML), визуализирующая поведение системы или объекта, показывая конечный набор их состояний и переходов между ними

![](Pasted%20image%2020260129192252.png)

##### тестирование состояний:

1. определить возможные состояния
2. определить, какие переходы между состояниями возможны
3. понять, какие действия приводят к переходам между состояниями



### процесс разработки тестов

#### этапы разработки тестов:

1. сбор информации
2. расставление приоритетов
3. оценка времени и рисков
4. оценка взаимосвязей
5. выбор стратегии и техники тестирования
6. критерии завершенности
#### сбор информации:

1. прочитать ТЗ
2. найти артефакты с предыдущий тестирований (если есть)
3. расспросить коллег, которые работали над задачей
#### приоритеты тестирования:

1. тест основного пользовательского/их сценария/ев
2. полная проверка задачи, как только по основному/ым сценарию/ям нет критичных проблем
#### критерии завершенности тестирования:

- закончилось отведенное на тестирование время
- проверены все критичные сценарии и исправлены все критичные баги
- другие критерии в зависимости от задачи



### классификация видов тестирования

#### по цели тестирования:
- функциональное (решает ли проблему пользователя, соблюдены ли требования, правильно ли реализована)
- нефункциональное (UI, usability, безопасность, производительность)
